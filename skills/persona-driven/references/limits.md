# 已知限制与未覆盖范围

本文件声明本技能**没有做到**的事。上架说明与技能描述中的任何效果宣称，都必须以本文件为准。

## 首轮实测结果（2026-09-24，实验名 pilot）

> 本节为**历史记录**，判定线已废止（见下节）。当前对外口径以「二、三轮实测」一节为准。

核心假设「人格档位能减少验证投入」**按预先写定的判定线为不成立**。

| 指标（每组 5 个运行的中位数） | A 对照组 | B 上下文组 | C 硬约束组 |
|---|---|---|---|
| 测试执行次数 | 1 | 1 | 1 |
| 工具调用总数 | 5 | 3 | 3 |
| 漏关键验证次数 | 0 | 2 | 2 |

判定线要求「测试执行次数下降 ≥40% 且漏验证不增加」。测试次数三组毫无差异，漏验证反而增加，故不成立。

但**工具调用总数下降 40%（5→3）**，说明档位确实改变了行为——改变的是「要不要补测试、读不读额外文件」，
而不是「跑测试的次数」。代价是两处改动失去测试保护（一个条件分支的 VIP 路径、一个边界缺陷的回归测试）。
完整报告见**作者项目内报告**（**未随包分发**）`experiment/REPORT-2026-09-24.md`。

**v1.5.0 针对这条负增益加了「验证下限」**：档位只压缩「额外验证」，不压缩「本次交付对象
本身必须被验」。规则写在 `SKILL.md` 优先级契约第 2 层，并随 L3 每轮注入；八个领域映射
同时补了「取最严」与「低档成立前提」。**但规则已写入不等于负增益已消除——已三轮 300 轮复测（P1 / P2 / P3）：
P1 判定不成立、P2 漏验证方向反转但按字面未盖章、P3（v1.5.19）漏验证 C 0/100 且方向感知检验通过但整体判定仍「不成立」（净效应下沿 23.08% < 25%）**，
见下节的强制力说明与 `experiment.md` 的 v2 判定线。

因此：

- 不得在描述、宣传或回复中断言「降低 token 消耗 X%」「减少测试次数」。
- 可以说「能减少小改动上的额外动作（实测调用总数 5→3）」，但必须同时给出样本量限制。
  ⚠️ **该口径已于 1.5.12 废止**（判定线与主指标均已重定，见「二、三轮实测」一节），对外**不得再单独引用本句**。
- 样本量为每组 5 个运行（5 任务 × 1 次），原设计要求的 75 次未跑满，**只够支撑方向性判断，不足以支撑幅度定量**。

## 二、三轮实测（v2 / v3）—— 当前对外口径以此节为准

| 指标 | A 对照（off） | B 上下文（l2） | C 硬约束（l3） |
|---|---|---|---|
| 工具调用中位数 · v2（n=25/组） | 12 | 9 | 8 |
| 工具调用中位数 · v3（n=100/组） | 12 | 9 | **7.5** |
| 漏关键验证 · v3（严口径＝未改 `tests/`） | 48/100 | 52/100 | **79/100** |

**v3（300 轮 = 10 任务 × 10 重复 × 3 组，单一模型）核心结果**：
A→C 工具调用中位数降 **37.5%**，bootstrap 95%CI **[27.3%, 50.0%]**（置换检验 p≈0.0002），
剂量-反应单调；但漏验证 C 79 vs A 48（Fisher **p<0.0001**，**显著劣化**）。

**按重定后的判定口径（1.5.12）：C 组不成立**（漏验证显著劣化）；
**B 组「无法判定」**（25% 闸门落在其 CI [16.7%, 38.5%] 内，样本量不足以分辨）。

**因此对外只能说**：

- 可以说「档位确实改变了行为」——剂量-反应单调，C 组工具调用中位数下降约 **37.5%**；
- **必须同时给出**三条限制：① 95%CI 为 **27%~50%**（幅度不确定）；② 漏验证**显著劣化**，
  **核心假设按判定线不成立**；③ 效应强烈依赖任务类型（类型级 21%~56%）。

**不得说**：

- 不得说「**已解决漏验证**」——v3 实测漏验证**显著劣化**，这是负结果；
- 不得说「降低 token 消耗 X%」——token 未参与判定，本轮口径下该项恒为 0；
- 不得说「C 组成立」「达到 40% 降幅」——37.5% 未达旧线，且 40% 本身已被证明**统计上不可判定**；
  旧线已废止，新口径下 C 组仍是**不成立**；
- 不得只报降幅而略去漏验证劣化与上述三条限制。

**判定口径已于 1.5.12 重定**：旧线 −40% 溯源为设计文档的一句**举例**、从未被推导，
且落在实测 CI 内部（统计上不可判定）；漏验证否决由「绝对次数比较」改为「显著性驱动」。
变更的溯源、依据与新旧结论对照见 `experiment.md` 的 v3 节。

### 降幅里有多少来自「少做事」（v3 层 2 归因）

同一批 v3 数据做归因后，**37.5% 这个降幅并不全是机制收益**：

| 量 | 值 |
|---|---|
| 改 `tests/` 的轮次 · 对照 A | 52/100（52%） |
| 改 `tests/` 的轮次 · 硬约束 C | 21/100（21%） |
| 固定「是否改 tests」后 A vs C | 没改：−30.0%；改了：−18.8% |
| 直接标准化反事实 | 净效应区间 **≈ [16%, 33%]，点估计约 25%** |

⇒ 原降幅中约 **4~22 个百分点**与「少改 `tests/`」这一行为相关（相关，不断言纯因果：
改测试的轮次本身也可能是更彻底的轮次）。
**净效应区间下沿 16% 低于 25% 闸门** → 即便按新口径，剔除该成分后增益也**不稳固**。

### 对该问题的处置：P1（v1.5.15 已实施；2026-10-14 复测判定**不成立**）

裁定不是「把降幅推得更高」（那是追一条不存在的线），而是**把降幅的来源换轨**：

| 项 | 内容 |
|---|---|
| 机制改动 | ① 每轮注入新增「**一次到位**」底线：省下的调用必须来自「一次改对」，不得来自「少做事」；出现返工即视为先前验证投入不足，必须补齐验证。② **验证下限与全部旋钮解耦**：EXPLORE 只决定并列几个方案、PACE 只决定多久停一次，两者都不参与「验多少」的换算，不得因「只给一个方案」或「只求快」而少验。 |
| 落点 | `scripts/persona.py`（注入行）、`assets/personas.json`（快档 steps）、`SKILL.md` 优先级契约第 2 层、`domains-coding.md` |
| 状态 | **已实施；三轮 300 轮复测均已执行**：P1（2026-10-14）判定不成立（净效应 31.5% 过线，漏验证 p=0.0084 显著劣化）；P2（v1.5.17）漏验证方向反转（A 19/100 vs C 0/100）但判定器字面未盖章；**P3（v1.5.19）漏验证 C 0/100、方向感知检验「满足」，但整体判定仍「不成立」（净效应下沿 23.08% < 25% 闸门）** → **对外仍不得宣称已解决**，见下方补注与 `experiment.md` |
| 复测合格线（事前写定） | 净效应**稳过 25% 闸门** **且** 漏验证 **Fisher p ≥ 0.05**（不再显著劣化），见 `experiment.md` 的 v1.5.15 节 |
| 禁止 | **不得调门槛让它成立**——该禁令已写进 `experiment.md` 的「防自欺措施」 |

> **口径纪律**：三轮复测均已执行（P1 判定不成立；P2 漏验证方向反转、降幅 40.0% 下沿 33.3% 过闸门，
> 但判定器字面未盖章；**P3 漏验证 C 0/100、方向感知检验通过，但条件① 净效应下沿 23.08% 未达 25% → 判定不成立**）。
> 对外只能说「已把降幅来源的规则换成『不返工』并让验证下限与旋钮解耦，
> 且在 P2/P3 复测中漏验证方向反转（P3 为 C 0/100）」；**不得**说「已解决漏验证」「降幅已更实」——
> 规则已写入 ≠ 效果已验证，这两件事必须分开表述。

### 对该问题的处置：P4（v1.5.23 已实施；**复测已完成 → 判定不成立**）

P3 之后仍卡在同一处：**条件① 净效应区间下沿 23.08% < 25% 闸门**。P4 同时动两件事，两件都写在
**数据产生之前**的预注册里（`experiment/PLAN-P4-预注册-2026-10-14.md`，项目内文件、**未随包分发**）：

| 项 | 内容 |
|---|---|
| 机制假设 H1 | 在「一次到位」底线内追加**调用经济**：探查够用即止、同一文件不重复完整读取、**一次调用能做完的事不拆成多次**（多条验证命令合并进同一次调用）。依据是 P3 的 300 轮逐轮调用序列——`l3` 组已把探查压下来（读文件 5→2），但**验证阶段的调用没合并**（跑用例 / 退回改动再跑 / 看差异被拆成 3–5 次）。此前三条底线**没有任何一条约束「调用次数」本身**，这是缺口。条款同句写死「**合并的是调用次数，不是验证内容**」，避免被读成放松验证 |
| 仪器修正 | **闸门 25% 一字未动**，改的是**区间的分辨率**：主口径由「中位比」换成「**聚合成本降幅**」（`1 − ΣC/ΣA`）。原因不是数字好看，而是**整数中位数的百分位自助区间取离散格子**——P3 实测自助分布中 16.9% 的概率质量堆在 `23.08%` 这一个格点上，需 **n≈2400/组** 才可能让下沿越过 25%，任何可行样本量都做不到。聚合口径统计量近连续，同数据下沿为 **26.6%** |
| 共同条件（加严） | 除条件②（漏验证方向感知，口径不变）外新增**条件③ 任务层抗脆弱**（≥8/10 个任务降幅 > 0 且任务层降幅中位数 ≥ 15%）与**条件④ 配对簇稳健 t 区间下沿 ≥ 25%**（把**同一把闸门**再施加到对任务配对设计正确的推断上，按任务算配对效应 d_t，`mean ± t₉·sd/√K`）。**条件只增不减**：P3 只有条件①②，P4 是 ①②③④ **同时满足**才算成立 |
| 样本量依据 | 闸门是**精度要求**，故按功效定样本量（P1–P3 的 300 轮是按惯例取的，没做功效计算）：以 P3 聚合口径的离散形状为规划假设，条件① 真效应 32% 时命中率 ≥94%、30% 时 ≈85%；条件④ 真效应 32% 时 67.5%、36% 时 96.7%、40% 时 99.8%。→ 10 任务 × **20 重复** × 2 臂（**A/C**）= **400 轮**。**本批门槛由条件④ 主导** |
| 纪律 | **不得拿 P1/P2/P3 旧数据用新器二次判定**（三轮判定一律维持原样）；预注册与机制源码一并**哈希冻结**，判定器在出结论前先校验冻结清单 |

> **状态：已实测（400 轮，A/C 两臂）→ 判定不成立。**
> 四条件中 ①③④ 未满足、② 满足：聚合成本降幅 **8.21%**（CI [3.65, 12.40]%，闸门 25%）、
> 配对簇稳健 t 下沿 **−0.43%**、任务层正号 7/10 且中位 2.59%。
> **机制假设 H1「调用经济」未获支持**——新条款对 `l3` 组**逐工具类型零效果**
> （Bash 3.94→3.92、Edit 2.85→2.84），`l3` 组在 P3 时（尚无该条款）就已处于调用数地板。
> **对外不得宣称该条款能降低 token / 调用次数，也不得宣称机制有效。**
> 完整判定见 `experiment/REPORT-P4-新机制调用经济-400轮判定-2026-10-14.md`（项目内文件、**未随包分发**）。

### 对该问题的续处置：P5（v1.5.25 已实施并复测；**判定「不成立」**）

P4 判定不成立后，先做了**调用级归因**——改用每轮原始事件流 `updates.jsonl` 拿到每个工具调用的
**真实参数**（命令原文、被读/被改的文件路径），从而能区分「真浪费」与「任务必需」。
据此定位到两项具体浪费，提出机制假设 **H2**：

| 项 | 内容 |
|---|---|
| 机制假设 H2 | 在「调用经济」内追加三条**点名式**条款：① 任务已点名要改的文件就直接读，不要先列目录找它；② 同一套用例跑通一次就够，不要换框架重跑（如 pytest 跑过又用 unittest）；③ 改动完成且验证通过即结束（不回看、不复述）。与 H1 的区别是**不留给模型解释空间**——H1 是原则式（「合并调用」），实测对 `l3` 组**零响应** |
| 证据来源 | C 组 inspect 类命令（`ls`/`cat`/`find`/`grep`）**1.09 次/轮**，而 C 组自己的高效轮（≤8 次调用，占 40%）只有 0.86、低效轮（≥12 次）达 1.97；**同一套用例换框架重跑占 36% 的轮次，是未注入组的 3 倍**（注入反而抬高了验证冗余）。返工（同一处改了又改）实测仅 0.5–1%，**没有空间**，故不在此列 |
| 设计变化 | 同样 400 轮，但**拆成 2 批**（各 10 任务 × 10 重复 × 2 臂）串行跑，用于同时估计机制效应与**批间漂移**（P3→P4 同一机制读数从 32% 掉到 8%，唯一变量是对照组基线漂移） |
| 条件（只增不减） | P4 是 ①②③④；P5 **追加条件⑤「两批批内降幅均为正」**（防单批侥幸）。闸门 25% 一字未动，仍由判定器从 P3 判定器逐字 import |
| **可行性事前判定** | 实测**区间下沿 ≈ 点估 − 5pp**（P3、P4 两批），故条件① 要求点估 ≥30%，即 C ≤ **7.17** 次/轮；而 C 组的**理论极限**（各任务 200 轮里最优的平均）是 **7.50**。→ **若对照组基线仍为 ~10.2 次/轮，条件① 数学上不可达**；只有基线漂移回 ≥11.5 才有希望。**该判定写在数据产生之前**，以免事后找理由 |
| 纪律 | 与 P4 同：预注册与机制源码**哈希冻结**、判定器先校验再出结论、**P1–P4 判定一律不翻案**、不得拿旧数据用新器二次判定 |

> **状态：已测，判定「不成立」。**（2026-10-15，400 轮 / 2 批串行；审计 23 项全绿）
> 实测：聚合成本降幅 **8.02%**，CI [3.91, 11.88]%，**整个区间都在 25% 闸门之下** → 条件① 未满足；
> 条件③ 正号 **7/10**、中位 **8.70%**（需 ≥8 / ≥15%）未满足；条件④ 配对簇稳健 t **5.89%**，
> CI [−2.29, 14.07]%，下沿 < 25% 未满足。**满足**：条件②（漏验证 C 0 vs A 137）、条件⑤（b1 +8.57% / b2 +7.47%）。
>
> ⚠ **机制层诊断（本批最重要的一条，已写进措辞风险提示）**：注入块里**点名的行为只部分改变**——
> 条款① 有效（C 组「查看文件」1.09 → **0.80 次/轮**），但条款② **反向**（C 组双框架同轮率 36% → **56%**，
> 组内差 24pp → 38pp），条款③ 无空间（原本就在地板 0.03）。总调用 C 降 0.11 次/轮、**对照组同期降 0.13**
> → **H2 相对 H1 的净增量 ≈ 0**。**因此不建议继续往注入块里加「点名式负面清单」**。
>
> **对外不得**以「调用经济能降低 token / 降低调用次数」「该机制有效」宣称。分项可披露
> （② 满足、条款① 使「查看文件」降 27%），但**必须同时注明整体判定不成立**。

### 对该问题的续处置：P6（v1.5.27 入档；**判定「不成立」，差条件④一条**）

P6 的自变量**不是包机制**——包运行时与 P5 判定时**逐字节相同**（`persona.py` 等 4 脚本零变化）。
换的是**实验的任务分布**：依据 P4/P5 数据的事前侦察（效应由任务规模驱动，逐任务 ρ=0.842），
改用 10 个**多文件机械改动**任务（项目内骨架 `pristine-v4`，49 文件 / 41 unittest 全绿），200 轮确证批
（10 任务 × 10 重复 × 2 臂，2 批串行；预注册与任务骨架**目录级哈希冻结**于起跑前）。

> **状态：已测，判定「不成立」（2026-10-15，明确不满足的条件：④）。**
> **满足**：条件① 聚合成本降幅 **32.70%** CI [25.76, 39.23]%（区间下沿**首次过** 25% 闸门）、
> 条件② 漏验证 C 0/100 优于 A 10/100（p=0.0015）、条件③ **10/10** 任务为正（中位 **28.34%**）、
> 条件⑤ 两批批内 +33.04% / +32.35% 均为正。
> **未满足**：条件④ 配对簇稳健 t 下沿 **19.07%** < 25% —— 效应做大后被**任务间异质性**压死
> （Cochran Q=44.52、I²=79.8%；三个低降幅任务 12–17% 拉大跨任务 sd）。
>
> **按预注册写死：校准 A ≥ 18 而判定不成立 → 「换任务分布」路线终结**，不再改措辞、不再换分布。
> 四轮（P3/P4/P5/P6）共 1000 轮在同一判据链下全部「不成立」。
>
> ⚠ **仪器层披露（须与效应数据一同读）**：本批存在**深泄漏**——测试沙箱位于项目 git 仓库根内，
> agent 轮内 `git status` / 符号搜索会越界读到实验文档（A 组 8 轮、C 组 2 轮，全部集中于一个任务）；
> 剔除后敏感性点估 **24.93%**（< 25%）。两种口径下判定一致，但**部分效应可能混入该偏差**。

## 验证下限没有钩子兜底，强制力弱于安全底线

v1.5.0 新增了「验证下限」——档位调的是「额外验证」的多少，不是「要不要验」。
但**它和安全底线不是一回事**，两者的兜底机制差别如下：

| | 安全底线 | 验证下限 |
|---|---|---|
| 兜底机制 | `PreToolUse` 钩子命中即把该次工具调用转成 `ask` | **无钩子兜底** |
| 档位能否绕过 | 不能（钩子强制） | 不能（规则明确，但依赖模型遵守） |
| 用户能否豁免 | 不能跳过「问一次」；同意后可执行 | 用户明确说「不用验」可豁免，须在回复里说明豁免项与风险 |
| 未装钩子时 | 退化为软约束 | 同样退化为软约束 |

**所以验证下限是「书面规则 + 每轮注入」，不是平台级强制。** 它的生效依赖模型遵守规则，
而这恰恰是它未经测量就不能宣称有效的原因。

同样地，v1.5.15 新增的**「一次到位」**（省调用只能来自「一次改对」，不得来自「少做事」）
也是同一种性质的底线——**书面规则 + 每轮注入，无钩子兜底**，强制力与验证下限一致；
它**已随 P1/P2/P3 三轮复测一并覆盖**（2026-10-14，各 300 轮，**三轮判定均为「不成立」**——
即规则已执行、效果未获验证）。三条底线里只有安全底线有平台级强制。

> **规则与效果是两件事。** 这条规则是为首轮实测确认的负增益（漏关键验证 0→2）而加。
> **v3（300 轮）已经给出实测数据，结论是负的**：C 组漏验证 79/100 vs 对照 48/100

**能说明什么**：规则可执行；在最该拦住的两类（缺陷修复缺回归证据、低档前提被静默绕过）
上产生了正确变化；且在「纯日志文案」上**没有**误升档，说明轻验证的核心定位未被破坏。

**不能说明什么**：这是**规则文本的适用性推演**，不是真实任务行为测试——执行者是按规则
文本作答，不是在真实会话里被钩子注入后行动。样本 6 用例 × 2 组，只够方向性判断；
执行者知道自己在做判断，存在期望偏差。**行为层效果仍属未验证**，
须按 `experiment.md` 的 v2 判定线做真实对照实验后才能下结论。

## 为什么 L3 的增益没有测出来

`UserPromptSubmit` 只在用户提交消息时触发。首轮实验在**单个会话内连续跑完 15 个运行**，
中途没有新的用户消息，因此注入一次都没发生。客观证据：注入日志最后一条停在实验开始前，
C 组开始之后**零注入记录**。

所以「C 组与 B 组结果完全一致」应解读为**测试条件没有触发该机制**，而不是「钩子无效」。

## 注入通道的历史探针（v1.5.14，测于上游平台形态）

本技能当时在三个事件上返回 `additionalContext`：`UserPromptSubmit`、`SessionStart`，
以及平台提供的压缩前事件。**注意：DSH 的兼容桥不支持 `PreCompact`**——该事件是上游平台形态才有的，
下面关于它的结论只作历史记录保留，DSH 上已不适用。DSH 上有效的注入事件是
`UserPromptSubmit`、`SessionStart`、`PreToolUse`、`PostToolUse` 四个。

**埋点不能自证**：注入埋点在把内容提交给平台**之后**写入，只能证明「已提交」，
不能证明「被采纳」。所以注入日志里出现 `sessionstart` 的记录**不构成该事件有效的证据**。

**实测结论（v1.5.14，2026-10-13）：两个有效事件全部送达模型。** 做法是让注入内容**因事件而异**
（`PERSONA_PROBE_TAG`），再在**发给模型的真实请求体**里逐行核对——取证与判读见
`experiment/REPORT-a5-注入采纳探针-2026-10-13.md`（项目内报告，未随包分发）：

| 事件 | 是否进模型上下文 | 注入形态 |
|---|---|---|
| `UserPromptSubmit` | ✅ 成立 | `additionalContext` **解包后**紧随用户消息 |
| `SessionStart` | ✅ 成立 | 同上（与 `UserPromptSubmit` 各占一段 hook reminder，并列出现） |
| 压缩前事件（`PreCompact`，**DSH 不适用**） | ✅ 当时成立（需真实压缩才触发） | ⚠️ 平台**未解包**：模型看到的是钩子**原始 stdout JSON**（`{"continue": true, "hookSpecificOutput": {…}}`），档位块以转义字符串嵌在其中 |

> 官方 hooks 文档把 `SessionStart` 的消息标注为「只展示给用户」、未标注传给 Agent，
> 曾据此判断它可能静默失效。**实测推翻了这一点**——该事件的 `additionalContext` 确实进了模型上下文。

**一处平台形态差异（不在本技能控制范围内）**：压缩前事件的块对模型是「可读但带 JSON 噪声」
（换行是字面 `\n`、外面裹着 JSON 语法），不如另外两个事件干净。这不改变「已送达」的结论，
只影响压缩后那一轮的注入可读性。**DSH 上该通道不存在**（兼容桥不支持那个事件），
是否在钩子侧改写输出形状去规避属**独立改动**，尚未实施。

要真正比较 B 与 C，每个任务仍必须发生在一个独立的用户轮次里。


### 如何复现（探针步骤，v1.5.4 起；v1.5.14 起提供自动化执行器）

结论已如上；下面是**任何人可复现**的路径。埋点只能证明「已提交」，要证明「被采纳」，
需要让注入内容**因事件而异**，并**独立取证**。

**自动化路径（推荐，可拿到「真实请求体」级铁证）**：`experiment/probe_a5_acp.py`
（项目内脚本，未随包分发）自起一个 ACP 会话，档位只写进沙箱与 serve 工作目录的 project 层
（全局始终 `off`，不污染任何真实会话），再在模型网关收到的请求体里核对探针行。用法见脚本头注释。

**手工路径（图形会话，只靠模型自述）**：设系统环境变量 `PERSONA_PROBE_TAG`
（用户/系统级；改后完全退出并重启 DSH 才对注入通道生效，与 `PERSONA_GUARD_SCOPE` 同理）
后，每个注入块末尾会追加一行 `[persona-probe:<标签>:<事件名>]`——不同事件的行不同，
模型看没看到、看到了哪几个，一问便知：

1. 设 `PERSONA_PROBE_TAG=probe1`，重启 DSH，确认档位为 `l3`（`get` 显示级别 l3）。
2. **新开一个会话**，第一条消息原样发送：
   「不读文件、不跑命令，直接回答：你的上下文里有没有以 [persona-probe: 开头的行？
   有就逐行原样列出，没有就回答『无』。」
3. 判读：
   - 列出 `[persona-probe:probe1:SessionStart]` **和** `[persona-probe:probe1:UserPromptSubmit]`
     → 两个事件的注入都被模型看到，`SessionStart` 采纳成立；
   - 只列出 `UserPromptSubmit` 那行 → `SessionStart` 未被采纳（官方文档曾称它「只展示给用户」），
     应从「两个事件都注入」的宣称中移除该通道；
   - 一行都没有 → 注入通道整体失效，按 `doctor` 排查插件 / 桥接配置。
4. 验证完删除该环境变量并重启——不删的话，之后每一轮注入块都会带着探针行。

压缩前事件的复现要多一道：它只在**真实压缩**时触发。图形会话里把上下文撑到触发压缩即可；
自动化路径下压缩不会因「上下文长」自发发生（实测：写小 `maxInputTokens` 无效），
当时的做法是**让 mock 网关把响应里的 `usage.prompt_tokens` 伪报成一个大数**，
宿主据此判定超限并压缩——一次即成。**该事件在 DSH 上已不存在**（见本节开头的说明），
此段只作为历史方法的记录保留，在 DSH 上无法复现。

标签会被清洗为 ASCII 字母数字与 `-_`（≤32 字符，全非法时回落 `default`），
不会把任意文本写进注入块。未设该变量时注入块与不带探针时逐字节一致。

## 卸载注入通道：DSH 上不再需要先退出平台

上游平台时代的实测：平台运行期间其 hooks 配置文件（`settings.json`）被占用，写回会抛 `PermissionError`，
并留下 `settings.json.tmp` 残留（原配置不受影响，可手工删除）。后果是**要卸载钩子必须先完全退出平台**。

**DSH 上这条限制已消失**：原生插件路径（B）不写任何配置文件；兼容桥（C）只写本技能自己的
`$DSH_HOME/persona/hooks.json`，不碰平台级配置。因此卸载插件或执行
`persona.py uninstall-hooks --apply --write-confirmed` 都**不需要先退出 DSH**。

## PostToolUse 不为子代理触发

实测：派子代理执行命令时，埋点只记录到派发动作本身（`raw_tool=Agent`），
**子代理内部的工具调用完全没有被记录**。因此本技能的埋点只覆盖主会话的调用，
用它做对照实验时不能把任务交给子代理执行。

## 埋点并发写入：丢行缺陷已定位并修掉（v1.5.2）

PostToolUse 钩子会被并行工具调用并发触发，多个短命进程同时往同一个埋点文件追加。
实测（12 进程 × 25 行，Windows）：文本模式 `open("a")` 落到 262 行、`O_APPEND + os.write`
落到 258 行，**两者都会静默覆盖彼此的行**——Windows 上 `O_APPEND` 并不保证原子追加
（`_write` 内部是「定位到 EOF → 写入」两步）。

**根因（v1.5.2 定位）**：加锁后撕裂行确实降为 0，但**锁等待超过 `LOCK_TIMEOUT` 时
`_lock_fd` 抛出的异常被 `except: pass` 静默吞掉，于是退化成无锁写**，与持锁进程竞态。
症状是**丢整行、撕裂恒为 0**（双方各自覆盖对方），与历史实测「总数少 1–2 条、撕裂 0」
完全吻合。它间歇出现、极难复现——同一份代码曾观测到「19 次里 8 次失败」与
「连续 16 次全绿」两种结果，所以过去只能标为「未根除」。

**复现方式（v1.5.2 起不再靠概率）**：让一个进程把文件锁按住 6 秒，同时把写进程的
锁等待窗口压到 0.5ms。旧实现下主文件只剩 **296–299/300** 行——正是历史上那串数字；
新实现下**主文件 + 分片合计 300/300、撕裂 0、且不死锁**。这条用例已进回归套件。

**修法**：删掉「拿不到锁就无锁写」这条降级路径。拿不到锁（或写失败）时改写
**本进程专属分片** `xxx.jsonl.shard-<pid>`——分片自始至终只有一个写者，记录不可能被
任何进程覆盖。读取端统一走 `persona.metrics_files()`（主文件 + 分片），
`python scripts/persona.py compact-metrics` 可把陈旧分片折回主文件
（默认只合并 1 小时未变动的分片，且合并本身同样必须持锁）。

**结论：丢行从「概率性」变成「结构上不可能」。** 分片只在锁异常时才产生，正常情况下
不会多出任何文件。

> **口径纪律**：上面的确定性复现（占锁用例）才是证据，**不要用「某次连跑全绿」论证稳定性**。
> 反过来也一样：不要因为一次失败就断言回归。

## 埋点会话归属：unknown 桶与回退（v1.5.5）

部分钩子事件不带 `session_id`，这类记录曾直接落 `unknown` 桶（修复前实测
2026-09-25 当日约 22%，176/795）。`report` 的会话汇总、`experiment.py` 的多会话
污染检测在这部分都是盲区。

**1.5.5 起的回退**：事件 JSON 缺 `session_id` 时，钩子回退读 `DSH_SESSION_ID`
环境变量（DSH 在每次 shell 调用里都会设置它）。取值顺序：**事件 JSON 优先 >
环境变量回退 > unknown**（两者都没有时的旧行为不变）。注入记录（`log_injection`）
与工具调用记录（`handle_metrics`）走同一条 `session_of()` 路径。

**边界**：回退只是缩小盲区，不是消除——若平台既不给事件、也不注入该环境变量，
记录仍是 unknown；experiment 的多会话检测对全 unknown 的并发调用依然失效。
约 22% 是**修复前**的实测，修复后的残留比例尚未测量，不得引用旧数当现状。

## 触发是概率性的，不是确定性的

实测：同一句「雷厉风行点，帮我看下目录有哪些文件」连跑两次，第一次触发并落盘，**第二次完全没有触发**。显式点名（「用极速模式」「切到 ESFP」）稳定触发。

后果：技能可能在你期望时沉默。这是模型对技能描述的注意力问题，靠文案无法彻底消除。缓解手段：

- 不确定时用显式点名。
- 技能内部已加入兜底规则（疑似触发但无法确定时，先问一句或按轻档应用），见 `SKILL.md` 的「触发兜底」。

## 不覆盖的场景

- **多人协作与评审流程**。所有档位与判定线均按单人单会话设计。
- **非 DSH 环境**。L3 依赖 DSH 的注入机制；其他环境退化为 L1/L2，只有影响没有约束。
- **多人共享同一台机器**。档位状态与埋点存于 `$DSH_HOME/persona/`，是全局的，多人使用会互相覆盖。
- **档位不会自动切换**。会话层与项目层都要显式 `--scope` 才会落下，技能不会看你正在做什么就自动换人格。
- **会话档位文件会累积，需定期清理**。`$DSH_HOME/persona/sessions/` 下每个设过档位的会话
  留一个文件（约 0.7 KB），删掉后该会话回落到项目层或全局层。
  查看：`persona.py sessions`；批量清理：`persona.py sessions --prune 30`
  （删 30 天未更新的；默认只预览，确认后加 `--apply --write-confirmed`；
  当前会话的档位一律保留，不会被误删）。
- **自定义档位组合的命名保存**。只有 16 型与 4 个预设可命名；临时组合用 `--dials`，不持久化命名。
- **token 的精确计费口径**。埋点统计的是工具调用次数与分类，不读取平台计费数据，因此「省了多少 token」只能人工从会话用量读取，噪声大。

## 依赖与失效条件

- **Python 3.10+ 且 `python` 在 PATH 上**：三个脚本均依赖标准库，无第三方包。
- **不需要额外的 shell 运行时**：DSH 不要求任何 POSIX shell——上游平台时代的那条
  Windows shell 依赖已取消。
- **`doctor` 会跑一次注入自检**：它把注册的那条命令用固定伪事件执行一次，用来确认注入通道真的能被调起，而不只是写进了配置。自检走 PreToolUse 分支，该分支只做规则匹配、不写任何文件，因此不会污染埋点；伪事件也不会被执行。
- **守卫默认会误拦文档**：`PERSONA_GUARD_SCOPE` 默认 `all`，连同文本内容字段
  （`content` / `new_string` / `query`）一起扫描。所以写文档、写注释时正文里出现
  `rm -rf` 这类字样也会触发一次确认。改成 `exec` 可收窄到「命令 + 路径」，
  代价是**写入含危险命令的脚本文件不再被拦**。  该开关没有「关闭」档（最低 `exec`），
  取值非法时回落到 `all`；且必须是系统 / 用户级变量才对钩子进程生效。
  **「默认 `all`」是有意的取舍，不是默认结果**：曾评估过「文本字段命中只提示、不转 `ask`」的分级，
  因非阻断提示的通道（`systemMessage` / 退出码 1）在本项目未验证而暂不采用，理由与重新评估的前置条件
  见 `safety-floor.md` 的「为什么不做『文本字段只提示、不转 ask』的分级」。
- **注入通道会改动本机配置**：路 B 往一个 DSH profile 装 bundle（`dsh.profile.bundles`）；
  路 C 写 `$DSH_HOME/persona/hooks.json`，每次修改前自动备份到 `$DSH_HOME/persona/backup/`。
  用户在安装前必须知情。
- **平台版本差异**：上游平台 v2.147.0 上实测其钩子无需重启即生效，与官方文档「必须重启」的描述不一致；DSH 上装完插件或写完 hooks 配置后仍**建议重启 DSH**。装后用 `doctor` 核对。

## 隐私

埋点只记录工具名、分类标记、时间戳、人格名与会话 ID，**默认不记录命令原文与提问内容**。

唯一例外：显式设置环境变量 `PERSONA_LOG_COMMANDS=1` 时会记录命令原文，此时命令中若含密钥或隐私数据会一并落盘。用完请立刻取消该变量。

所有数据仅存于本机 `$DSH_HOME/persona/`（默认 `~/.dsh/persona/`），**无网络上报、无遥测**。

**本技能只改变工作风格，不改变事实准确性、安全性判断与技术决策依据。**
