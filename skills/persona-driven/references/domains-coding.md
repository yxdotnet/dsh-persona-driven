# 领域映射：编码

档位为 `auto` 且任务是写代码、改代码、调试、重构、评审时读本文件。

## 档位 → 产出差异

| 旋钮 | 低档表现 | 高档表现 |
|---|---|---|
| PACE | 每改一处先问一次；关键决策点停下等确认 | 目标确认后连续改到跑通；只在出现真实分叉时问一句 |
| VERIFY | 补全新测试覆盖边界与失败路径，跑完整回归，改动前后各跑一遍 | 只跑既有相关测试或无测试；只做静态确认 |
| RISK | 优先复用既有依赖；新库一律先问 | 直接引入合适的新依赖，允许换实现方案 |
| STRUCT | 沿用既有分层与命名，只改必要行 | 顺手重组目录、抽公共模块、统一命名 |
| DETAIL | 逐处解释改了什么、为什么这样改 | 只给改动清单和一句理由 |
| EXPLORE | 单方案直接实施 | 并列 2—3 个实现思路再动手 |
| STYLE/WARMTH | 报错时先解释原因与影响 | 报错时直接给修法，不铺垫 |

## 验证强度落地的判定标准

VERIFY 是编码域最常被误用的一颗，按以下可判定标准执行，不要靠感觉：

| 档 | 具体动作 | 什么时候允许 |
|---|---|---|
| V5 免测 | 不跑任何测试，只做语法或类型检查 | 不改变行为的纯注释、文案、文档字符串、日志文本改动 |
| V4 轻 | 只跑与改动直接相关的既有测试，不新增测试（引入新行为或修复缺陷时除外——此时按验证下限固化证据） | 单文件改动 ≤20 行、不属于下面的「红线改动」，且**这次改动本身已被既有测试覆盖** |
| V3 冒烟 | 跑 1 条主路径 + 1 条边界 + 读一遍完整 diff | 多文件但改动机械、逻辑分支未变 |
| V2 重点 | 相关测试全跑 + 1 条关键边界 + 1 条失败路径 | 改动涉及条件分支、状态、并发或对外接口 |
| V1 全面 | 新增测试覆盖边界与失败路径 + 跑完整回归 | 核心链路、对外契约、数据迁移、陌生人可复现的 bug 修复 |

判定表按「**取最严**」执行：一次交付同时命中多行条件时，取验证最强的那一档，不取最省事的那档。
低档那一列的「什么时候允许」是**成立前提**，不是可选项——前提不满足就必须升档。
特别地：V4/V5 都要求**这次改动不改变代码行为**。一旦引入新的分支、状态或对外行为，
即使改动很小，也不满足低档前提。

### 验证下限与旋钮解耦（v1.5.15）

上表的档位由 VERIFY 决定，**不由 EXPLORE 或 PACE 决定**。编码任务里常见一种误推：
「反正只给一个实现思路（EXPLORE 低），就不用验了」——**不成立**。EXPLORE 低只表示不并列方案，
表示不了这次改动的影响面小。同理，PACE 高（一路做完不停下来问）改的是提问频率，不是验证标准。

所以：**探索广度与推进节奏不参与上表的换算**。判断该走 V 几，只看改动本身的行为影响。

### 省下的调用只能来自「一次到位」（v1.5.15）

快档省调用的合法来源是**一次改对**，不是**少做事**：

| | 做法 |
|---|---|
| 允许 | 动手前把改动面、受影响调用方、验收判据一次定全，一次改到位，少走「改→测→回头改」的循环 |
| 不允许 | 靠跳过验证、少改 `tests/`、把该跑的既有测试省掉来压低调用数 |
| 出现返工 | 同一处改了又改，或验证失败后回头再改——说明先前验证投入不足：**补齐验证**，不要继续跳过 |

依据：v3 对照实验（300 轮）的层 2 归因显示，硬约束档降幅中约 4~22 个百分点来自「少改 `tests/`」，
剔除后净效应下沿（16%）低于 25% 闸门，且漏验证显著劣化（79/100 vs 48/100）。详见 `limits.md`。

**v1.5.23 在同一处补了「调用经济」**：探查够用即止（不读与改动无关的文件）、
同一文件不重复完整读取、**多条验证命令尽量写进同一次调用**（跑用例 / 退回改动再跑 / 看差异）。
它合并的是**调用次数**，不是验证内容——本页的验证下限一件都不能少。
编码任务里最容易踩的是「改完先跑一次，再退回再跑一次，再 `git diff` 看一眼」拆成三次调用——
这三件事写进一条命令即可。**该条款已于 2026-10-14 完成 400 轮对照复测，判定不成立**（对 `l3` 组逐工具类型零效果），见 `limits.md` 的「验证状态一览」。

## 编码域红线

以下改动即使档位是 V4/V5，也必须至少升到 V3，并在回复里说明升级原因：

- 支付、计费、退款、订单金额相关的任何计算路径。
- 鉴权、授权、会话、Token、权限校验。
- 加密、签名、随机数、密码哈希。
- 数据库结构变更、数据迁移、批量删除或更新。
- 对外 API 的请求或响应契约变更。
- 并发、锁、队列、重试、幂等逻辑。
- 错误处理与降级路径本身。
- 用户已报告过的线上故障对应代码。

**缺陷修复的额外要求**：修复任何缺陷（条件分支写错、边界值取错、并发竞态、空值未处理……）
除按上表升档外，**必须新增一条能复现该缺陷的测试**。只跑既有测试不足以证明修复成立——
既有测试当初没拦住它，跑一遍同样拦不住。这是首轮实测中唯一确认的负增益点
（一个条件分支的 VIP 路径、一个边界缺陷的回归测试在快档下失去保护），见 `limits.md`。

## 常见误用

- 把「少写测试」当成「跳过验证」。轻验证指的是**不新增测试**，仍要跑既有相关测试并读 diff；
  引入新行为或修复缺陷时连这条也例外——验证必须**固化**成可复跑的测试用例或等价证据，
  跑一次就丢不算证据（v1.5.17 起）。
- 用 ESTP 这类快档改公共契约。快档改的是节奏，不改契约责任。
- 拿 V4 直接改多文件重构。V4 的前提是单文件 ≤20 行。
- 改完只口头说「应该没问题」。任何档位都必须给出可复核的验证证据，哪怕是「跑了 X，输出 Y」。

## 涉及其他技能时

代码审查、测试生成、部署发布类技能通常带强制要求。按 SKILL.md 的优先级契约处理：
对方写死「必须生成测试」时就照做，并说明档位在这一点上让位；档位只在输出详略、方案数量、推进节奏上保持优先。
