# 领域映射：计划与排期

档位为 `auto` 且任务是排期、拆任务、定里程碑、估工时、给交付日期、调整计划时读本文件。

## 档位 → 产出差异

| 旋钮 | 低档表现 | 高档表现 |
|---|---|---|
| PACE | 每给一个里程碑停下等确认，逐段往下排 | 一次给完整排期并连续拆完，只在出现真实分叉时问一句 |
| VERIFY | 逐条核对依赖闭包、资源占用、关键路径与失败预案，标出每处不确定 | 只做一次可行性直觉判断，直接落日期 |
| RISK | 只排已验证过的路径，不为新做法承诺工期 | 允许把未验证的新路径排进关键路径，且不留缓冲 |
| STRUCT | 沿用既有里程碑定义、阶段划分与排期模板 | 重划阶段、改里程碑口径、重定义交付单元 |
| DETAIL | 每个任务给负责人、工时假设、前置依赖与验收标准 | 只给里程碑名称与日期清单 |
| EXPLORE | 只给一条排期路径 | 给主计划、备选路径，以及切换触发条件 |
| STYLE | 平铺事实与假设，不加判断 | 直接点出计划里最脆弱的一环，并给态度 |
| WARMTH | 直接说排期不现实，不铺垫 | 先承认对方的时间压力，再谈取舍 |

## 验证强度落地的判定标准

VERIFY 在计划域的含义是**计划自检的投入**。按以下可判定标准执行，不要靠感觉：

| 档 | 具体动作 | 什么时候允许 |
|---|---|---|
| V5 直觉 | 只做一次可行性直觉判断，不列依赖、不标假设 | 个人一次性任务，无对外承诺、无跨人依赖，错了可随手改 |
| V4 单点 | 核对一条关键前置与自身可用资源是否够 | 单人 3 天以内、不牵动他人排期的短计划 |
| V3 清单 | 逐条列出任务清单并核对直接前置依赖 | 多人参与但依赖不跨团队、无外部日期承诺 |
| V2 重点 | 依赖闭包 + 资源冲突检查 + 关键路径识别 | 有对外日期、跨团队依赖，或存在并行资源争用 |
| V1 全面 | 在 V2 基础上补失败预案、备选路径与切换触发条件，逐条标注估算假设 | 对外承诺的交付、多团队联调、不可延期节点 |

判定表按「**取最严**」执行：一次交付同时命中多行条件时，取验证最强的那一档，不取最省事的那档。
低档那一列的「什么时候允许」是**成立前提**，不是可选项——前提不满足就必须升档。
特别地：V4/V5 都要求**这次改动不改变计划语义**。一旦引入新的里程碑、依赖或工作量估算，
即使改动很小，也不满足低档前提。

## 计划与排期域红线

以下场景即使档位是 V4/V5，也必须至少升到 V2，并在计划里写明升级原因：

- 对外或对上级承诺的交付日期：标注估算假设与不确定性区间，不得只给一个无假设的确定日期。
- 跨团队、跨部门依赖：显式列出对方交付物与所需时间，不得默认对方随时可配合。
- 资源冲突未解决（同一人或同一环境被并行占用）：解决前不得宣称计划可行。
- 关键路径上存在未验证的新做法：给出该环节的失败预案与回退路径。
- 合同、验收、发版、监管报备等有硬截止的节点。
- 计划变更波及已对他人承诺的日期：重排依赖并重新通知相关方，不得只改自己的日期。

本域原则：**不确定性必须外显**。宁可给区间加假设，也不给一个看着确定的单点。

## 常见误用

- 把快档当成「给一个确定日期」。快档压缩的是流程，不是不确定性，日期仍要带假设与区间。
- 用 V5 的直觉判断给跨团队排期背书。直觉判断只对单人、无承诺的任务成立。
- 用户尚未确认方案就把排期往下推，把待定项写成已定项。
- 计划变更时只改日期，不重排依赖、不通知受影响的人。
- 用「先这样排着」回避依赖闭包检查，把风险留给执行阶段。

## 涉及其他技能时

项目管理、甘特图、里程碑模板、任务拆解类技能通常带强制格式或字段要求。按 SKILL.md 的优先级契约处理：
对方写死「必须填依赖字段或画甘特图」时就照做，并说明档位在这一点上让位；档位只在日期颗粒度、方案数量、
推进节奏与不确定性标注方式上保持优先。两者直接冲突且都明确时，停下问用户一句。
