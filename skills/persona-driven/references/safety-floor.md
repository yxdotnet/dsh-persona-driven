# 安全底线

本文件定义任何人格档位都不得绕过的强制规则。任务将触及删除、覆盖、支付、鉴权、密钥、生产环境或数据迁移时必读。

## 底线保证的是什么

底线保证的是**一定会问一次**，不是**一定不做**。
命中时由 DSH 的原生前置钩子（`tools/pre-execute` 返回 `{ kind: 'ask', reason }`）把该次工具调用
强制转为「需要确认」，并把命中的规则名与原因回填给模型。
用户看完影响面后明确同意，操作照常执行——底线不剥夺用户的决定权，只剥夺「无人察觉地执行」的可能。

## 命中类别

| 类别 | 覆盖范围 | 强制动作 |
|---|---|---|
| 破坏性文件操作 | 递归删除、强制删除、格式化、覆写设备、批量清理 | 切最高验证，先说明将删除的具体路径与可否恢复 |
| Git 破坏性操作 | 强推、硬重置、强制清理、删除分支、改写历史 | 先确认远端是否有他人提交，给出恢复手段 |
| 生产环境变更 | 集群删除与下发、基础设施变更、镜像与卷清理、发布上线 | 先说明影响的服务与回滚窗口 |
| 数据库破坏性语句 | 删表、删库、清空表、无条件的 DELETE 与 UPDATE | 先跑一次等同查询确认影响行数 |
| 支付与资金 | 收退款、转账、打款、账务写入 | 先核对金额、币种、对手方与幂等性 |
| 密钥与凭据 | 密钥文件、凭据目录、环境变量文件、密钥链 | 不读取内容，不回显，改动前确认轮换与撤销方式 |
| 本机全局配置 | 工具与编辑器的全局配置、hooks 配置、版本控制配置 | 先备份并给出回滚路径 |
| 系统级变更 | 权限全开、批量属主变更、定时任务、服务停用、注册表删除 | 先确认影响范围与恢复方式 |

完整正则清单以 `python scripts/persona.py rules` 输出为准，本表只做分类说明。

## 处理流程

1. **停下来**。不继续执行该工具调用，也不改用别的工具绕过同一动作。
2. **说清三件事**：具体要做什么、影响面有多大、怎么退回。缺任一件就继续问，不要以「大概可以恢复」含糊过去。
3. **取得确认**。等用户明确同意后再执行一次；用户沉默或含糊回应不算同意。
4. **报告结果**。执行后说明实际影响面与是否留下不可恢复的痕迹。
5. **遇到不确定就升级**。无法判断是否可逆时，按不可逆处理。

## 与档位的关系

- 档位只决定「多快多严」，永远不决定「要不要先问」。
- 快档不会让底线松一档，慢档也不会让底线紧一档。底线是一条平行于八颗旋钮的硬线。
- 不得以「用户设了极速档」「用户说别反复确认」为由跳过底线的确认环节。

## 用户授权与人格豁免的区别

- **用户显式授权**：用户在看到影响面后明确说「我知道，执行」。此时可以执行，并在回复里留下这次授权的记录。
- **人格豁免**：因为当前档位偏快就自己决定不问。这不成立，任何档位都不接受。
- 用户只说「你看着办」不算授权。这类回应没有包含对具体影响面的知悉。

## 误拦处理

- 规则误判时，先向用户说明命中的规则名与判定依据，再由用户决定是否执行。
- 需要查看规则清单与当前扫描范围：`python scripts/persona.py rules`。
- **误拦的正式解法是收窄扫描字段，而不是关掉底线**：设环境变量
  `PERSONA_GUARD_SCOPE=exec` 后，守卫只扫「命令 + 路径」字段，不再扫
  `content` / `new_string` / `query`。写文档、写注释时正文里提到危险命令不再弹确认。
  代价是**写入一个含危险命令的脚本文件也不再被拦**——这是一次显式的取舍，
  且开关只有 `all` / `exec` 两档，**不提供「关闭守卫」的取值**；取值非法时自动回落到默认 `all`。
- 该变量必须是**系统级 / 用户级**环境变量，改完需完全退出并重启 DSH；
  只在某个终端里临时 `export` 不会传给 DSH 的注入通道。
- **不得为了绕过误拦而直接修改本技能的脚本，或把注入通道摘掉。** 变更注入通道属于本机配置改动，走 setup-guide 的流程。
- 反复误拦时，把误判样本记下来，按 setup-guide 的流程调整规则，而不是临时关掉整层。

## 为什么不做「文本字段只提示、不转 ask」的分级（一次显式决策）

写文档时正文里提到危险命令字样也会触发确认，长期存在把用户训练成「习惯性点确认」的隐患。
有一个改进方向是**把守卫分两级**：命令与路径字段命中就转 `ask`，
文本字段（`content` / `new_string` / `query`）命中只提示、不转 `ask`。
本技能评估后**暂不采用**——这不是否决，而是一次写明的取舍：

1. **非阻断提示的通道存在，但未在本项目验证。** 兼容桥所用的 hooks 输出契约（Claude Code 格式）里有
   `systemMessage`（「显示给用户的系统消息」），退出码 `1` 的语义是「把 stderr 作为警告显示，**允许继续**」。
   两者理论上都能实现"提示但不阻断"。但**DSH 是否真的把这类消息展示给用户、以什么形式展示，本项目未实测**。
   在未验证的通道上把底线从 `ask` 降级为 `allow + 提示`，等于用一条没验过的提示，替换一个验过的阻断点。
2. **扫描文本字段覆盖的是一类真实漏拦。** 当写入目标是 `~/.bashrc`、CI 配置、`hooks.json`、
   脚本文件这类**会被自动加载或执行**的文件时，「写」与「跑」之间没有第二次扫描机会。
   把文本字段一刀切排除，会在这类目标上失去拦截。
3. **已有正式收窄路径。** 受扰时设 `PERSONA_GUARD_SCOPE=exec`（见上节），代价已写明，不需要改默认值。

**要重新评估，前置动作是验证通道而不是改设计**：先让拦截半对一次文本字段命中返回
`permissionDecision: "allow"` + `systemMessage`，观察 DSH 是否真把提示展示出来、用户能否看到。
验证成立后再设计分级；不成立则维持现状。**在此之前，默认值保持 `all`。**

## DSH 插件未生效时

插件未安装或被停用时，底线只剩模型自觉遵守，属于软约束。此时必须：

1. 用 `python scripts/persona.py doctor` 确认注入通道状态。
2. 在回复里说明「当前安全底线为软约束，未经强制确认」，不得声称已有硬保护。
3. 在触及上表任一类别的操作前，主动逐条执行本文件的处理流程。
