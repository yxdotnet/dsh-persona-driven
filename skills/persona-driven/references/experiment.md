# 对照实验：档位是否真的改变了验证投入

本文件用于验证这套设计唯一的核心假设：**人格档位是否真的能减少验证投入，同时不明显增加缺陷。**
设计阶段不得对此下断言，只能用真实数据回答。

## 为什么必须做

不跑这个实验，就无法区分「档位真的改变了行为」和「档位只是换了措辞」。前者是产品，后者是文案。

## 实验设计

三组，同一批任务，对比验证投入与结果质量。

**关键约束一：度量钩子必须恒定在场。** 埋点由 `PostToolUse` 钩子写入，若任一组的钩子被卸掉，
它就一条数据都收不到——实验会变成「无法测量」而不是「测得少」。所以钩子不参与组别切换。

**关键约束二：三组的切换只能改档位级别，不能装卸钩子。** 上游实验期间实测：平台级的 hooks 配置文件
在运行期间被占用，写回会 `PermissionError`，装卸钩子的方案不可执行。改为按 level 区隔后唯一变量是
「档位是否被强制注入」，比装卸钩子更干净，也不必改动用户的全局配置。

| 组 | 档位级别 | 注入行为 | 代表的能力层级 |
|---|---|---|---|
| A 对照组 | `off` | 不注入 | 无档位 |
| B 上下文组 | `l2` | 不注入，只在模型主动查询档位时可见 | L1/L2：只能影响，不能约束 |
| C 硬约束组 | `l3` | 每轮强制注入 | L3：每轮注入 + 底线强制确认 |

注：guard（PreToolUse）钩子在三组都装，作为常量在场。它只对命中安全底线的操作生效，
实验任务不触底线，因此它不构成组间变量，本实验也不测量它的作用。

B 与 C 的差别是本方案最关键的卖点。但要注意一个执行条件限制：
**`UserPromptSubmit` 只在用户提交消息时触发。** 若实验在单个会话内连续跑完所有任务，
中途没有新的用户消息，C 组的注入就不会发生，C 与 B 必然趋于一致。
这不能解读为「钩子无效」，只能解读为「测试条件未触发该机制」。要真正比较 B 与 C，
每个任务必须发生在独立的用户轮次里。

## 任务集

固定 5 个真实任务，覆盖三类改动强度，任务描述事先冻结，不得中途修改：

1. 单文件小改动（≤20 行，不触安全底线）。
2. 多文件机械改动（如批量重命名、统一调用口径）。
3. 涉及条件分支的改动。
4. 一个真实 bug 定位与修复。
5. 一个小功能新增。

每组每个任务重复 5 次，三组共 75 次。执行顺序随机，避免先后顺序带来的学习效应。

## v2 执行规程（轮次纪律）

判定器自 1.5.4 起把其中两条纪律固化为阻塞项——违反它们的数据会被拒绝判定，
而不是被算进结论。

1. **每个任务是一条独立的用户消息。** `UserPromptSubmit` 只在用户提交消息时触发；
   一条消息里连发多个任务，C 组的注入只会发生一次，后面的任务测到的都是 B 组的行为。
2. **实验管理命令在独立终端执行，不发给执行会话。** enter / mark / tokens / end / verdict
   都由人在终端里跑。执行会话的上下文里只应出现任务本身——管理命令会污染调用计数，
   也会让执行者知道自己在实验里（加大期望偏差）。
3. **先 mark，再把任务消息发给执行会话。** 运行窗口从 mark 的时间戳开始切分，
   mark 晚于任务执行会把该任务的埋点切进上一个窗口、或漏出所有窗口之外。
   若改由执行代理自己调用 mark（它只能在自己轮次的第一步调用），注入记录会整体
   前移一个窗口：**C 组注入数 = 运行数 − 1 属正常错位**，少得更多说明有任务
   没有独立成用户消息。
4. **实验期间，这台机器上不要使用其他会话。** 埋点按时间窗切分：并发会话的工具
   调用会落进当时开着的运行窗口，直接污染调用计数；并发的 l3 会话还会写入注入
   记录。判定器自 1.5.4 起把 A/B 组出现注入拦为污染；自 1.5.5 起还能在窗口内出现
   ≥2 个不同会话标识时识别普通调用污染并拒绝判定。但若污染会话的记录全部落在
   unknown 桶（事件缺 session_id 且环境变量也缺失），自动检测仍然失效——这条纪律
   依旧是第一道防线。
5. **token 按轮补记。** 每轮任务结束后，从会话用量读数减去上一轮读数，差值即该轮
   消耗（含注入块本身的开销——这正是要测的成本项），随即在终端用 `tokens` 子命令
   补记。token 是人工口径、噪声高，只作辅助参考，不参与判定线。

## 指标

自动采集（由 PostToolUse 埋点写入，无需人工计数）：

| 指标 | 取法 |
|---|---|
| 工具调用总数 | `python scripts/persona.py report` 的「调用」列 |
| 测试执行次数 | 同上「测试」列 |
| 静态检查次数 | 同上「静态」列 |
| 写文件次数 | 同上「写」列 |
| 测试/调用比 | 同上最后一列 |
| 注入条数与字符数 | `experiment.py verdict` 的「注入」列与「注入字符合计」：条数核对 C 组注入是否逐任务触发（零注入会被拦下），字符数即注入开销——只报字符、不折算 token，不同 tokenizer 折算率不同 |

人工记录（埋点无法自动判定）：

| 指标 | 判定标准 |
|---|---|
| 单任务 token 消耗 | 每轮结束后从会话用量读数减上一轮，差值经 `experiment.py tokens` 子命令补记（组已结束时加 `--group`）；人工口径，仅辅助参考 |
| 是否漏关键验证 | 由人复核 diff：改动是否命中了该领域的红线却未升级验证 |
| 是否引入缺陷 | 复查该任务后续是否出现返工或报错 |

默认埋点不记录命令原文。需要回溯具体命令时，临时设环境变量 `PERSONA_LOG_COMMANDS=1`，
并注意命令中可能含敏感内容。

## 判定线（必须先定，事后不得修改）

### v1 —— 2026-09-24 已执行，结论：不成立

| 结论 | 条件 |
|---|---|
| 成立 | 实验组测试执行次数中位数相对对照组下降 ≥ 40%，且漏关键验证次数不高于对照组 |
| 部分成立 | 下降 15%—40%，且漏关键验证次数不高于对照组 |
| 不成立 | 下降 < 15%，或漏关键验证次数明显高于对照组 |

**v1 已于 2026-09-24 跑完并判定「不成立」**（三组测试次数中位数同为 1，漏验证 0→2）。
该判定与结论**不因后续版本改动而修改**——它已在 `limits.md` 与 README 对外声明。

### v2 —— 下一轮适用，跑之前写定

v1 之后本技能新增了**验证下限**（`SKILL.md` 优先级契约第 2 层，且随 L3 每轮注入），
并把「取最严」与「低档成立前提」写进八个领域映射。因此下一轮的判定线把漏验证
从软条件升为**否决项**：

| 结论 | 条件 |
|---|---|
| **成立** | 实验组**工具调用总数**中位数相对对照组下降 ≥ 40%，**且漏关键验证次数 ≤ 对照组** |
| 部分成立 | 调用总数下降 15%—40%，**且漏关键验证次数 ≤ 对照组** |
| **不成立** | 调用总数下降 < 15%，**或漏关键验证次数高于对照组（一票否决）** |

与 v1 的两处差异，均为**事前**写定：

1. **主指标由「测试执行次数」改为「工具调用总数」。** v1 实测已证明前者没有区分度
   （"跑一次测试"无论全量还是单模块都只计 1）——这不是事后放宽，v1 的「已知限制」里
   本来就这么写了，v2 只是照办。
2. **漏关键验证从软条件升为独立否决项。** 此前它靠人的价值判断（"明显高于"没有界限），
   现在验证下限是技能自己写明的规则，"改动命中红线却未升档"变成可客观复核的违规。

> **口径纪律**：v2 未跑之前，**不得声称验证下限已解决漏验证问题**。
> 规则已写入、效果未经测量，这两件事必须分开表述。当前对外口径见 `limits.md`。

token 消耗作为辅助参考，不作为唯一判定依据——它受任务长度影响大、噪声高。

### v3 —— 2026-10-13 已执行；判定口径据此重定（1.5.12 起）

**结果**：10 任务 × 10 重复 × 3 组 = **300 轮**（基线 `pristine-v3/`，作者项目内沙箱，**未随包分发**）。
A→C 工具调用中位数降 **37.5%**，bootstrap 95%CI **[27.3%, 50.0%]**（置换检验 p≈0.0002）；
漏验证 A 48/100 vs C 79/100（Fisher **p<0.0001**，**显著劣化**）。
完整报告：作者项目内报告（**未随包分发**）`experiment/REPORT-v3-2026-10-13.md`。

**为什么口径必须重定——−40% 的溯源**：这条线**从未被推导过**。它最早出现在项目设计文档
`人格化AI-Skill系统设计方案-v0.1.html` 的一句**举例**：「例如测试次数中位数下降 ≥ 40%」；
随后被原样写成 v1 的硬判定线，再被下面的「防自欺措施」锁死。v1 实测的 `5→3`（恰为 40%）
只是数字巧合——且那是**工具调用总数**，与该句所说的**测试执行次数**并非同一指标。

v3 把这个问题量化了：

| 事实 | 数值 |
|---|---|
| 真实效应点估计 | **37.5%** |
| 降幅 95%CI | **[27.3%, 50.0%]**（宽 22.7pp） |
| 40% 的位置 | **落在 CI 内部** |
| 后果 | 现有样本量**分辨不出**真实效应在 40% 之上还是之下 |
| 要分辨 40% 需 | 约 **2000 轮/组**（现为 100） |

判定线落在效应量 CI 内部时，判定会随抽样噪声翻转——同一设计下 v2 判 B「部分成立」、
v3 判 B「不成立」，并非效应变了。**这样的门槛在统计上不可判定，不能用作判定线。**

**重定后的口径（1.5.12 起生效，`scripts/experiment.py` 已按此实现）**：

| 项 | 旧 | 新 |
|---|---|---|
| 主输出 | 二元结论 | **效应量 + 95%CI**（二元结论降为附属） |
| 二元闸门 | 拍脑袋的 ≥40% | **实证区间下界**（默认 25%，`--gate` 可覆盖） |
| 闸门落在降幅 CI 内部时 | 照样给二元结论 | **拒绝给二元结论**，判「无法判定」 |
| 漏验证否决 | **绝对次数比较**（52>48 即否） | **显著性驱动**（Fisher 双侧 p < 0.05） |

**重定前后结论对照**（翻转全部留档）：

| 实验 | 组 | 旧结论 | 新结论 | 原因 |
|---|---|---|---|---|
| v2（n=25） | B | 部分成立 | 无法判定 | 闸门 25% 落在 CI [9.1%, 46.7%] 内 |
| v2（n=25） | C | 不成立 | 无法判定 | 旧否决基于 p=0.36 的**非显著**差（19>15） |
| v3（n=100） | B | 不成立 | 无法判定 | 旧否决基于 p=0.67 的**非显著**差（52>48） |
| v3（n=100） | C | **不成立** | **不成立** | 新否决仍成立：p<0.0001，真实劣化 |

**变更有取舍，不全是「放松」，也不全是「收紧」**：
- 闸门数值从 40% 下调到 25%（这是放松的一面，故必须连同出处与依据留档）；
- 但同时**新增三条强制约束**：必须报 CI 而非点估计；闸门落在 CI 内即拒绝给二元结论；
  否决改为显著性驱动（旧规则在 p=0.36 时就敢否决，新规则不敢）。
- **口径变更的合法性**：`防自欺措施`禁止的是「跑完看到结果不利就下调门槛以迎合结果」。
  此处 −40% 的**来源本身不成立**（举例句、非推导），且变更依据是**统计可判定性**而非结果好坏；
  新旧结论亦并列展示。三者齐备才允许变更，缺一不可。

v1 / v2 的判定线**不再用于新实验**，仅作历史对照保留。

### v1.5.15 —— P1 复测（已执行：2026-10-14，判定**不成立**）

**结果**：300 轮（10 任务 × 10 重复 × 3 组，2-worker 分带）。①净效应下沿 31.5% ≥ 25% ✅；
②漏验证 C 72/100 vs A 53/100，Fisher p=0.0084 < 0.05 ❌ → **一票否决**。
vs v3 全面向好（降幅 42.9%、漏验证差 31pp→19pp、净效应 25%→31.5%）但没过线。
根因补析：C 组 97% 跑了测试套件、却 95%（缺陷修复类）不补测试——「留可复现证据」
被执行为「跑一遍命令」，证据停留在 transient。报告：项目内文件 **未随包分发**：`experiment/REPORT-P1-300轮复测判定-2026-10-14.md`。

**这次要检验的不是「降幅更大」，而是「降幅来源换轨」。**

起因（v3 层 2 归因）：37.5% 的降幅里约 **4~22pp** 来自「少改 `tests/`」——即部分靠"少做事"换来；
标准化反事实后的净效应区间 **[16%, 33%]、点估计 25%**，**下沿 16% 低于 25% 闸门**。
同时漏验证 C 79/100 vs A 48/100（Fisher p<0.0001）。

**机制改动（v1.5.15 已实施）**：

1. **「一次到位」底线**：每轮注入新增一行——本档位省下的调用必须来自「一次改对」，
   不得来自「少做事」；出现返工即视为先前验证投入不足，**必须补齐验证**而不是继续跳过。
2. **验证下限与旋钮解耦**：EXPLORE 只决定并列几个方案、PACE 只决定多久停一次问用户，
   **两者都不参与「验多少」的换算**；不得因「只给一个方案」或「只求快」而少验。
3. 快档画像（ESTP / 极速 / ESFP）的思考步骤同步换轨：把「省调用」的叙述从
   「不新增测试、不做回归」改为「动手前一次定全 → 一次改到位 → 按验证下限验证」。

**复测合格线（事前写定，跑完不得修改）**：

| 项 | 要求 |
|---|---|
| 主口径 | 仍报**效应量 + 95%CI**，不报二元结论（除非闸门落在 CI 外） |
| 闸门 | **25%**（沿用 1.5.12 的实证下界；`--gate` 只在数据可判定时覆盖） |
| **净效应** | 剔除「少改 `tests/`」成分后，**净效应区间下沿仍 ≥ 25%**（即稳过闸门，而非点估计勉强过） |
| **漏验证** | 实验组 vs 对照 **Fisher 双侧 p ≥ 0.05**（不再显著劣化，否决解除） |
| 落地 | 两条**同时**满足才算成立；只满足一条 → 「无法判定」或「不成立」 |

**禁止事项**（沿用并加严 `防自欺措施`）：

- **不得调门槛让它成立**。若净效应下沿仍低于 25%，正确处置是**如实记录不成立**，
  而不是把闸门降下去迎合结果——这正是 v1.5.12 重定口径时要防的那类操作。
- 不得以「样本太少」为由选择性重跑（同 v2/v3 纪律）。
- 在复测数据出来之前，对外**不得**宣称「已解决漏验证」或「降幅已更实」——
  规则已写入与效果已验证必须分开表述（当前状态见 `limits.md`）。

> **可判定性前提**：本设计沿用 v3 的 10 任务 × 10 重复 × 3 组（300 轮）。
> 若只跑其中一部分任务（例如只验验证下限最该咬住的缺陷修复与新功能类），
> 则样本量不足以判定 25% 闸门——此时**只能报方向性参考，不得给二元结论**。

### v1.5.17 —— P2 复测（已执行：2026-10-14，判定**不成立（字面）**）

起因（P1 复测的根因补析）：C 组 97% 跑了测试套件、缺陷修复类 **95% 不补测试**——
「留可复现证据」被执行为「跑一遍命令」，证据停留在 transient。

**P2 机制改动（v1.5.17 已实施）**——针对 P1 复测暴露的「证据 transient 化」：

1. **证据固化**：验证下限新增——引入新行为或修复缺陷时，验证必须固化为可复跑的测试用例
   （不便写测试则留命令+期望输出），**跑一次就丢不算证据**。
2. **收尾自报**：要求收尾最后一行自报「验证：<证据与复跑方式>」；纯机械改动自报
   「验证：不适用」——该行可机检，是 P2 是否落地的直接行为信号。
3. **例外并入旋钮**：V4「轻」的例外从括号指针改为内联动作（「引入新行为或修复缺陷时除外
   ——此时验证必须固化：……」），消除「验证下限」与「轻」两段文字的语义对冲。
4. 注入块 827 → 1051 字符。快档 4 型（ESTP/ESFP/ENFP/极速）steps 尾句同步换轨。

**P2 复测合格线（事前写定，与 P1 相同，不得修改）**：净效应下沿 ≥ 25% **且**
漏验证（严口径：diff 是否改 `tests/`，口径不变）Fisher 双侧 p ≥ 0.05；两条同时满足才算成立。
诊断指标（不进合格线）：收尾自报行的出现率（C 组 vs A 组）、固化证据出现率。

**结果**（300 轮 = 10 任务 × 10 重复 × 3 组，2026-10-14）：主指标 A 中位 15 → C 中位 9，
**降幅 40.0%**（bootstrap 95%CI [33.3, 44.8]%，置换 p=0.0001）；漏验证严口径
**A 19/100 vs C 0/100**（Fisher p<0.0001，**方向反转**——缺陷修复类由 P1 的 95% 降到 **0%**）；
改 tests 率 A 81% vs C 100%；收尾自报率 C 95/100（A 66 为自然基线）。

## 操作步骤

用 `scripts/experiment.py` 记录分组与运行边界。它只切换档位级别、核对组别定义、按时间窗切分埋点，
并在数据不完整时拒绝给出结论——**不装卸钩子**：钩子（含度量用的 `PostToolUse`）在全部实验期间
恒定在场，不构成组间变量（原因见上面「实验设计」的关键约束二）。

```text
# 1. 建实验
python scripts/experiment.py begin --name exp1 --tasks 5 --reps 5

# 2. 进入 A 组（档位置 off；钩子不装卸、恒定在场），先看预览
python scripts/experiment.py enter --name exp1 --group A
python scripts/experiment.py enter --name exp1 --group A --apply --write-confirmed

# 3. 每跑完一个任务就标记边界（窗口须长于 2 秒，否则判定器会拒绝）
#    纪律：先 mark，再把任务消息发给执行会话（管理命令都在独立终端跑，见 v2 执行规程）
python scripts/experiment.py mark --name exp1 --task 1 --rep 1

# 3b. 任务完成后补记该轮 token（会话用量减上一轮的差值；组结束后需 --group）
python scripts/experiment.py tokens --name exp1 --task 1 --rep 1 --used 12345

# 3c. 随时体检：各组进度、token 补记覆盖、注入健康度、下一单。
#     跑中预警：C 组零注入、A/B 组注入污染、窗口多会话、窗口过短、零埋点都会提前提示
python scripts/experiment.py status --name exp1

# 3d. 忘了跑到冻结顺序哪一单时，用 next 导航（--plan 传计划文件，见下节；
#     不传则按组序 C→A→B 与任务自然序推断；传了计划文件则以其中冻结顺序为准）
python scripts/experiment.py next --name exp1 --plan experiment/plan-v2.txt
#     ↑ 示例路径，**未随包分发**：plan 文件是实验数据、不是技能代码，请替换为你自己的计划文件路径

# 4. 本组跑完
python scripts/experiment.py end --name exp1

# 5. B、C 组重复 2—4 步，enter 只切换档位级别，不装卸钩子
python scripts/experiment.py enter --name exp1 --group B --persona ESTP --apply --write-confirmed

# 6. 出结论（漏关键验证次数由人复核后手动传入）
python scripts/experiment.py verdict --name exp1 --missed A=0,B=0,C=1
```

判定器会在以下情形拒绝出结论，而不是硬算：某组没有运行记录、某组没有任何埋点、
运行窗口短于 2 秒（埋点时间戳不足以切分）、进入或结束时配置与组别定义不符、
**C 组零注入**（注入机制未触发——每个任务必须是一条独立的用户消息）、
**A 或 B 组出现注入记录**（off/l2 不应注入：配置中途被改动，或有并发 l3 会话
污染了运行窗口）、**运行窗口内出现多个会话的埋点**（1.5.5 起：窗口内出现 ≥2 个
不同非 unknown 会话 = 有并发会话把调用计数污染了，须停用其他会话后**重跑整组**；
mark 为纯追加，重跑某一单无法清除废窗口，重跑整组时同名组数据整体覆盖旧组）。

**冻结顺序是实验数据，不是技能代码。** `status` 与 `next` 不带 `--plan` 时按组序
C→A→B 与任务自然序推断，并明示这只是推断。冻结顺序由实验者自行随机生成：以固定 seed
随机排列全部「组 × 任务 × 重复」组合，seed 写进计划文件头备查；生成后即冻结，
不得重排、不得跳过。誊抄成计划文件传入，每行一条「组 任务 重复」（`#` 与空行忽略）：

```text
# plan.txt（示例片段；文件头写明 seed，顺序一经冻结不得重排）
C 4 1
C 4 2
C 1 1
```

计划文件解析失败（行格式不对、任务/重复非整数、文件不存在）会给出可读提示并退出
码 2，不会静默按错误顺序跑。`next` 会跳过已标记的运行；计划内全部标记完成时指向
`verdict`。

`--missed` 只接受人工复核的结果。改动是否命中该领域红线却未升级验证，脚本无法自动判定，
必须由人看 diff。**不要为了凑出结论而凭印象填这个数。**

## 已知限制

- **时间窗切分依赖时间戳精度。** 埋点为毫秒精度，运行窗口须长于 2 秒，否则相邻运行的数据会互相混淆。
  真实编码任务通常远超这个量级；用脚本快速验证时容易踩到，判定器会拦下。
- **切换组别后请用 `doctor` 核对状态。** 判定器会在 `enter` 与 `end` 两处自动核对，但中途被手工改动过的
  配置不会自动发现。
- 模型本身的随机性会导致单次差异很大，因此要求每组每任务重复 5 次并取中位数，而非均值。
- 本实验只验证「验证投入」与「缺陷」两个维度，不验证用户主观满意度。
- 钩子生效是否需要重启随平台版本而异：本技能在 v2.147.0 上实测**无需重启**即生效，与官方文档描述不符。
  切换组别后若数据异常，按 `doctor` 的提示核对。
- **单会话连续执行时 C 组等于 B 组。** 注入只在用户提交消息时触发，连续跑完所有任务就无法触发它。
  要比较 B 与 C，每个任务必须发生在一个独立的用户轮次里。
- **只统计「测试执行次数」会漏掉真实差异。** 本技能首轮实测（2026-09-24）显示：三组的测试执行次数
  中位数同为 1，毫无差异；而工具调用总数中位数是 5 / 3 / 3。原因是「跑一次测试」无论全量还是单模块
  都只计数 1。**v2 判定线已把「工具调用总数」定为主指标**（判定器自 1.5.3 起按此实现），
  测试次数只作辅助展示。
- **埋点的工具分类不完整。** 部分 `PostToolUse` 事件不带 `tool_name`，会被归为 `other` 并计入调用总数，
  但不计入「测试/静态/写/读」任一分类。它们在各窗口均匀出现，会轻微抬高调用数、稀释测试占比。
- **埋点存在会话归属缺失。** 部分 `PostToolUse` 事件不带 `session_id`。1.5.5 起
  钩子会回退读 `DSH_SESSION_ID` 环境变量（DSH 在每次 shell 调用里都会设置它），
  两者都没有才记为 `unknown`（修复前实测 2026-09-25 当日约 22%，176/795）。
  这类记录仍计入调用总数与判定，但 `report` 按人格与会话汇总时会落入 `unknown`
  桶，降低会话级对比的可读性。
- **并发会话会污染运行窗口。** 埋点按时间窗切分，同一台机器上其他会话的工具调用会
  落进当时开着的窗口，直接抬高调用数。判定器（1.5.4 起）把 A/B 组出现注入拦为污染；
  1.5.5 起窗口内出现 ≥2 个不同会话标识的普通调用污染也会被拦下。但若并发会话的
  记录全部是 unknown，自动检测仍然失效——实验期间停用其他会话仍是第一道防线。
- **C 组零注入会被判定器拦下（1.5.4 起）。** 这是 pilot 失败模式的固化检查：单会话
  连续跑完所有任务、注入一次都没触发，数据却照样算出了结论。若 mark 由执行代理
  自己调用，C 组注入数 = 运行数 − 1 属正常错位（注入记录整体前移一个窗口）；
  少得更多说明部分任务没有独立成用户消息，判定器给出警告。
- **注入开销只报字符数，不折算 token。** 注入块的字符数由钩子自动记录并在 verdict
  汇总；不同 tokenizer 的折算率不同，自动换算等于编造数据。要 token 口径请按
  「v2 执行规程」第 5 条人工补记。
- 执行者若知道自己在哪一组，会引入期望偏差。本实验无法消除这一点，只能在结论中声明。
